# VK Insight — Agent Skill

Консольное приложение на Laravel 9.x для анализа VK. Все команды запускаются из корня проекта через `php artisan`.

## Быстрый старт: три команды для любой задачи

1. **Загрузить данные** → `vk:posts-get --owner=... --from=... --db`
2. **Проанализировать** → `vk:analytics --owner=... --period=... --compare=previous`
3. **Найти контент** → `vk:word ...` или `vk:candidate ...`

## Типичные сценарии

### Сценарий 1: «Упал охват» (проверка гипотезы о снижении ER)

```
# Шаг 1. Загрузить свежие посты за нужный период
php artisan vk:posts-get --owner=-12345678 --from=2026-06-01 --to=2026-08-01 --db --clear

# Шаг 2. Сравнить с предыдущим периодом
php artisan vk:analytics --owner=-12345678 --period=2026-06-01:2026-08-01 --compare=previous

# Шаг 3. Если данных мало — расширить период
php artisan vk:analytics --owner=-12345678 --period=quarter --compare=previous --best-time
```

**Интерпретация:**
- Смотри на `Сравнение с предыдущим периодом` — стрелки ⬆️/⬇️ покажут динамику
- Если средний ER упал >20% — гипотеза подтверждается
- Проверь `ER по дням недели` — возможно, изменился паттерн публикаций
- Для групп используй отрицательный owner_id (`-12345678`), для личных страниц — положительный (`12217086`)

**Что ещё проверить при падении охвата:**
```
# Статистику через stats.get (требует право stats у токена)
php artisan vk:stats-get --group-id=12345678 --from=2026-06-01 --to=2026-08-01 --interval=month --extended

# Исторический ER (точнее, использует подписчиков на дату поста)
php artisan vk:analytics --owner=-12345678 --period=quarter --use-stats --compare=previous
```

### Сценарий 2: «Лучшее время для поста»

```
php artisan vk:analytics --owner=-12345678 --period=quarter --best-time
# Требуется минимум 3 поста в каждом часе для статистической значимости
```

### Сценарий 3: «Найти контент для репоста»

```
# Поиск по слову в БД (быстро)
php artisan vk:word концерт --owner=-12345678 --from=2026-01-01 --db

# Поиск кандидатов без репостов
php artisan vk:candidate --owner=-12345678 --noreposts
```

### Сценарий 4: «Ротация постов в отслеживаемых группах»

Основной workflow для републикации контента:

```
# Шаг 1. Для каждой отслеживаемой группы найти ранние посты с низким охватом
php artisan vk:early-posts --owner=-154303482 --max-reposts=1 --limit=10

# Вывод: ID | Дата | Текст | Лайки | Репосты | ⇨ | Просмотры | URL
# Важно: в выводе есть id записи в БД и ссылка на оригинальный пост

# Шаг 2. Пользователь выбирает пост, делает репост вручную в VK

# Шаг 3. СНАЧАЛА проверить, что пост реально опубликован в группе:
php artisan vk:posts-get --owner=-154303482 --from=today --format=json
# → убедиться, что в ответе есть пост с тем же текстом, что и републикуемый

# Шаг 4. ТОЛЬКО если публикация подтверждена — удалить пост из БД
php artisan vk:post-delete 82060

# Удаление с подтверждением. Выводит URL оригинала для удаления из VK.
# Dry-run для проверки: php artisan vk:post-delete 82060 --dry-run
```

**Важно:** после `vk:post-delete` нужно вручную удалить оригинальный пост в VK по ссылке из вывода.

**Правила для агента:**
- ВСЕГДА дублируй URL оригинального поста в тексте ответа, не полагайся только на таблицу
- **Формат вывода выборки:** сначала таблица с колонками (ID, Дата, Текст, Лайки, Репосты, Просмотры) БЕЗ колонки URL, затем отдельный блок «Ссылки на оригиналы:» со списком `- ID: https://vk.com/wall-...` под таблицей. Не вставляй URL внутрь таблицы — это ухудшает читаемость.
- После `vk:post-delete` явно напомни удалить оригинал в VK
- **Проверяй публикацию ДО удаления из БД.** Порядок: (1) пользователь говорит «провёл републикацию ID X» → (2) проверь `vk:posts-get --owner=<группа> --from=today --format=json` → (3) если текст нового поста совпадает с текстом X — выполняй `vk:post-delete X` (с подтверждением); если пост НЕ найден или текст не совпадает — НЕ удаляй, сообщи пользователю, что публикация не подтверждена
- **Видео-посты:** у видео-постов текст в БД может быть коротким заголовком («Женовач об отношениях с артистами»), а при републикации пользователь добавляет транскрипт видео как текст. В этом случае ищи совпадение по СМЫСЛУ (тема/персона), а не по тексту. Если сомневаешься — спроси пользователя.
- На фразу «продолжить ротацию» — НЕ угадывай группу. Спроси пользователя: «Для какой группы делать выборку?» и предложи прочитать `resources/vk-groups.csv`. Если в сессии уже были обработанные группы — перечисли их и спроси, какую следующую.

### Сценарий 5: «Анализ ядра лайкнувших» (сегментация аудитории)

```
# Базовый анализ (k=1 — минимум 1 друг среди лайкнувших)
php artisan vk:likers-core --owner=-670335 --post=37732 --delay=0.5

# С повышенным порогом (k=2) + демография
php artisan vk:likers-core --owner=-670335 --post=37732 --k=2 --delay=0.5 --demographics

# Экспорт в markdown
php artisan vk:likers-core --owner=-670335 --post=37732 --k=2 --output=likers.md
```

**Что делает:** получает список лайкнувших пост, для каждого проверяет `friends.get`, находит пользователей с ≥k друзей среди других лайкнувших. С флагом `--demographics` добавляет распределение по полу и возрасту.

**Сегменты аудитории (три уровня):**

| Сегмент | Кто | Что означает |
|---|---|---|
| Ядро (k≥2) | Люди с ≥2 друзей среди лайкнувших | Связанное сообщество: сотрудники, актёры, лояльные зрители, фанаты |
| Скрытые | `friends.get` вернул ошибку (закрытый список друзей) | Более приватная часть аудитории |
| Открытые | Остальные | Чистый органический охват без связей внутри сообщества |

**Интерпретация демографии (`--demographics`):**

- `users.get` (демография) и `friends.get` (ядро) — **независимые** запросы. Закрытые друзья ≠ закрытый профиль. Возраст может быть известен даже для «скрытых».
- Доля скрывших возраст — сама по себе сигнал. Если 40%+ не показывают год рождения → аудитория возрастная (40+, чаще женщины).
- Типичный профиль театральной аудитории: женщины 45+, 40-60% скрывают возраст (диапазон по трём постам).
- Рост доли скрытых профилей → контент резонирует с интровертной/закрытой частью аудитории.

**Методологические оговорки:**
- Ядро (k≥2) — **нижняя оценка**. Скрытые не проверены на k≥2, часть из них может быть в ядре.
- Средний возраст — **по указавшим год рождения**, смещён в сторону открытых профилей.
- Выводы о форматах на ≤3 постах — **гипотезы**, не факты. Нельзя отделить формат от содержания, времени и продвижения.
- «Нет профиля» (users.get) ≠ «скрытые друзья» (friends.get) — разные уровни приватности.
- Сегменты всегда взаимоисключающие — проверка целостности встроена в команду.

**Важно:**
- Всегда `--delay=0.5` или выше — `friends.get` для каждого лайкнувшего быстро упирается в rate limit. При 58 лайках: ~30 сек, при 125: ~1 мин.
- **НИКОГДА не запускай `vk:likers-core` параллельно** (несколько постов/групп одновременно). Процессы делят один токен, внутренняя задержка бесполезна — данные будут испорчены rate-limit-ошибками. Только последовательно.

### Сценарий 6: «Продольный анализ ядра» (матрица переходов)

```
# Шаг 1. Накопить данные через vk:likers-core для нескольких постов
for pid in 37662 37665 37678 37679 37732; do
  php artisan vk:likers-core --owner=-670335 --post=$pid --k=2 --demographics --delay=1.0
done

# Шаг 2. Построить матрицу переходов
php artisan vk:core-transitions --owner=-670335 --window=5
```

**Что делает:** показывает, как пользователи переходят между сегментами (core/open/hidden) от поста к посту. Вычисляет устойчивое ядро — пользователей с ≥2 попаданиями в ядро внутри скользящего окна.

**Интерпретация:**
- `core→core: N` — лояльное ядро возвращается
- `open→core: M` — новобранцы (реальные, через лайк)
- `open→absent: K` — разовая аудитория, не вернулась
- `hidden→hidden: L` — приватная часть аудитории стабильна
- Устойчивое ядро — более надёжная оценка связанного сообщества, чем «вечное» ядро (k≥2 во всех постах)

**Важно:** hidden-переходы (`core→hidden`, `hidden→core`) часто отражают смену приватности, а не реальный вход/выход из ядра — интерпретировать осторожно.

## Команды: шпаргалка

| Команда | Когда использовать | Ключевые опции |
|---|---|---|
| `vk:posts-get` | Загрузить посты в БД | `--owner`, `--from`, `--to`, `--db`, `--clear` |
| `vk:posts-get-all` | Загрузить посты для ВСЕХ групп из vk-groups.csv | `--from`, `--delay=0.5` |
| `vk:analytics` | Анализ ER, лучшее время, топ-посты | `--period`, `--compare=previous`, `--best-time`, `--use-stats` |
| `vk:stats-get` | Статистика охвата/посетителей (stats.get) | `--group-id`, `--from`, `--interval`, `--extended` |
| `vk:word` | Поиск постов по слову | `word`, `--owner`, `--from`, `--db` |
| `vk:candidate` | Поиск кандидатов для репоста | `--owner`, `--noreposts` |
| `vk:check` | Мониторинг последних постов групп | `--cached`, `--format=json`, `--output=` |
| `vk:token-check` | Проверить права токена | `--token=`, `--format=json` |
| `vk:groups-info` | Информация о группах из CSV | (без параметров) |
| `vk:likers-core` | Ядро лайкнувших + демография | `--owner`, `--post`, `--k=2`, `--delay=0.5`, `--demographics` |
| `vk:core-transitions` | Матрица переходов + устойчивое ядро | `--owner`, `--window=10`, `--min-core-posts=2` |
| `vk:early-posts` | Ранние посты с низкими репостами (для ротации) | `--owner`, `--max-reposts=1`, `--limit=10`, `--offset=0`, `--from`, `--to` |
| `vk:post-delete` | Удалить пост из БД после републикации | `id`, `--dry-run` |

## Важные параметры

- **`--owner`** — для групп отрицательный ID (`-12345678`), для пользователей положительный (`12217086`)
- **`--from` / `--to`** — даты: `YYYY-MM-DD`, относительные (`today`, `yesterday`, `last week`, `last month`). Правая граница **не включается** (полуоткрытый интервал)
- **`--period`** — пресеты: `week`, `month`, `quarter`, `year` или диапазон `YYYY-MM-DD:YYYY-MM-DD`
- **`--db`** — сохранить/читать из БД (таблица `vk_posts`). Намного быстрее API
- **`--clear`** — удалить старые посты перед загрузкой (только для указанного owner_id и периода)
- **`--delay`** — задержка между запросами (сек). Есть только у `vk:posts-get-all` и `vk:check`
- **`--offset`** — смещение для пагинации в `vk:early-posts` (по умолчанию 0)

## Данные и файлы

- **Отслеживаемые группы:** `resources/vk-groups.csv` — группы постоянного мониторинга. `vk:check` и `vk:posts-get-all` работают именно с ними. Остальные группы запрашиваются разово через `vk:posts-get --owner=...`
- **БД:** MySQL `vk_insight`, таблицы: `vk_posts` (посты), `vk_check_cache` (кеш проверок)
- **Конфиг:** `config/vk.php` — токен, таймауты, таймзона аналитики
- **Токен:** `VK_TOKEN` в `.env`

## Диагностика

```
# Проверить, загружены ли данные
php artisan tinker --execute="echo DB::table('vk_posts')->where('owner_id', '-12345678')->count();"

# Проверить права токена
php artisan vk:token-check

# Загрузить посты для всех групп разом
php artisan vk:posts-get-all --from="last month" --delay=0.5
```

## Ограничения

- Для свежего анализа всегда нужно сначала загрузить данные через `vk:posts-get --db`
- ER по умолчанию использует **текущее** количество подписчиков — для старых периодов включай `--use-stats`
- VK API имеет rate limits — используй `--delay=0.5` для массовых операций
- **Просмотры/охват (views/reach):**
  - Для **личных аккаунтов** — недоступны через VK API в принципе. `wall.get` возвращает только реакции (лайки, репосты, комментарии)
  - Для **групп** — доступны через `vk:stats-get`, но требуют прав администратора группы у токена
  - `vk:analytics` всегда считает ER только по реакциям, а не по просмотрам
- `ER = (лайки + репосты + комментарии) / подписчики × 100%` — формула завышает значения при малой базе подписчиков (<100)
- **Автоматическая публикация** (`vk:post-repost`) требует community access token с правом `manage` — текущий user token не подходит, команда не используется
